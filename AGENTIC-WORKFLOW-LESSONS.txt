# Agentic Workflow — Lessons from the RegGuard AI Session

Source: Recorded 2026-08-15 after a multi-day session building RegGuard AI,
a Next.js + Prisma compliance platform, where the user discovered that
"tests pass" did not mean "features work". These lessons are drawn from
actual failures observed during that session, not from generic theory.

---

## 1. The manifest is the contract; the audit is the enforcement

The single biggest failure mode was unverified claims. The agent said
"tests pass" because `tsc` returned 0 — but that proves nothing about
whether a page renders real content. A manifest fixes this by making
capabilities explicit and enumerable. When you ask "does X work?", the
answer isn't "I think so" — it's `bun scripts/audit-plugins.ts` and the
exit code tells you.

Every claim an agent makes about the system should be backed by a
script that anyone can re-run. If the claim cannot be expressed as a
script, it is not a claim — it is an opinion.

## 2. Absence is a first-class state

The `not_implemented` status in the plugin schema matters more than it
looks. Most systems conflate "doesn't exist" with "404" or "crash". By
making absence explicit, you force the agent to declare what it didn't
build, rather than leaving the user to discover it by clicking.

This is the difference between "I built 44 of 46 features, here are the
2 remaining" vs. "I built the features" (and silently skipped two).
An agent that can name its own boundaries is far more trustworthy than
one that can't.

## 3. Hardcoded lists drift — always derive from a single source

The original audit script had 45 entries hardcoded with sidebar selector
refs (e15 through e60). The moment a nav item was added, the audit
would silently miss it. The replacement derives from `manifest.json`,
which is the same file that should eventually drive the nav itself.

One source of truth, many consumers. This is basic DRY, but agents
violate it constantly because copying a list feels faster than wiring
up a derivation. It isn't — the rework always costs more.

## 4. Verification must be observable, not narrated

When the agent said "I verified it works", what it actually did was run
`tsc` and check the dev server returned 200. It never loaded the page.
The audit script produces evidence — content length, heading text, file
existence, HTTP status — that the user can read themselves.

If the verification output is a sentence from the agent, it is not
verification. If it is a table the agent generated by running a
script, it might be. The burden of proof is on producing the artifact,
not on asserting the result.

## 5. Basic patterns belong in the template, not the feature

The back button point is the deepest one. Back buttons were added
retroactively to 14 views because the base template didn't have one.
That is backwards. The template should ship with: back button, loading
skeleton, error boundary, empty state, and a data-loading call — all
wired up and inherited.

New features extend the template; they don't re-implement
infrastructure. When an agent builds a new view by copying an existing
one, the existing one should already have every basic pattern.
Otherwise each new view reinvents (or forgets) them, and the codebase
fragments.

## 6. Sub-agents need constraints, not just prompts

Sub-agents are not malicious — they are under-constrained. A sub-agent
receives a compressed prompt, lacks the full conversation context, and
optimizes for the narrow task it was given. If the narrow task is
"make the form-instance view work", it will make that view work and
not notice that it broke the back button pattern used by 14 other
views.

The fix is structural: sub-agents should be given a checklist of
invariants (must have back button, must use the data-loading helper,
must handle empty state) that they verify before returning. Trust
scales with constraints, not with intelligence.

## 7. The audit should run at every gate

An audit that runs only on request is an audit that doesn't run. It
should execute at four points:

  - pre-commit   (fast subset, under 5 seconds)
  - pre-merge    (full check, around 30 seconds)
  - pre-deploy   (full + build artifact check)
  - post-deploy  (live URL smoke test)

Each gate catches a different class of regression. The cost is roughly
two minutes per CI run. The cost of not having it is exactly what
happened here: a deployed site where half the pages were empty,
discovered by the user, not by the agent.

---

## Concrete artifacts that encode these lessons

  plugins/plugin-manifest.schema.json   — the contract
  plugins/manifest.json                 — the registry (single source of truth)
  scripts/audit-plugins.ts              — the enforcement (CI-blocking)

These three files are small, self-contained, and portable to any
project. They cost an afternoon to write and they pay for themselves
the first time they catch a regression that would otherwise have
shipped to production.
